# Proof — two tiers, red→green, the measurement export

## §1 Tiers and what the gate enforces (R16)

Tier per file = `high` when `risk ≥ 2`, or a `proof.tiers.high.paths` match, or `security_sensitive`; else `light`. `forge proof tier --file <path> --risk <0-3> [--security] [--cwd <dir>]` prints it; it is decided at `review-file` time, recorded, and the block gate enforces the union.

| tier | proof required | when |
|---|---|---|
| light | red→green recommended for every new or changed test; **optional at the gate** | the coder or orchestrator runs the runner per test (§2) |
| high | red→green **required at the gate** for every changed high-tier file, plus the deeper **review** depth of `review.md` §2 (two lenses and a judge) | as above; `block close` refuses `unproven <file>` |

**`forge block close` enforces the high tier:** tier inputs are `proof.tiers.high.paths` (the union of the config at the block's base and the current one), the recorded `risk`, and `security_sensitive`; a row naming the file whose MAC fails makes it high. Each changed high-tier file needs a signed `proof` row of this run and block with `step: red-green`, `proven: true`, `red_kind: assertion` whose `covers` list names the file (`revert` covers the sources it put back; `assertion-deletion` covers only its test), else `unproven <file>`; only the human's `forge block waive <id> proof --file <path>` clears it.

**Mutation testing is not part of this product.** The question whether tool-made mutants on changed lines (Infection, Stryker) should be a user-facing proof tier was decided: **cut**. There is no `proof mutate`, no nightly mutation run, no `min_msi` floor, and no mutation-tool key in `.code-forge.yml`; a consumer that runs a mutation tool does so outside code-forge and never beside a coder's test run in the same tree. What replaces it as proof is the rule itself: one exact test per acceptance clause plus one negative or boundary where the clause has a failure mode — assertions that say **which** element and **how many**, never merely whether something exists — and the isolated per-file review with the convergence rule, which on this package's own build found the defects green suites had missed.

`proof.extra` (an argv array) keeps a consumer's legacy proof commands running inside the gate.

## §2 Red→green — journaled, killable, RED must mean an assertion

**One call proves one test** — a test file, or one case of it (`<file>::<case>` is the label) — with one of two mechanisms: `revert` (the block's changed source files are put back to their base version, so the test must fail against the code it was written for) or `assertion-deletion` (a characterization test, proven by deleting its assertions). The runner does not distinguish a new test from a changed one: the caller runs it once per test the acceptance names, new or changed alike, and the count of `RED` rows is the count of proven tests — there is no separate "new cases" tally. In this version the runner is invoked per test from the coder's or the orchestrator's side; the block gate reads the resulting signed `proof` rows but does not launch the runner itself.

The runner works in the export (§3) or under the lock with a journal: it refuses when a journal already exists (an earlier run was interrupted) → journals every source file the test covers (bytes, sha256, mode — or `existed: false`) → writes the **base** version of each (`git show <base>:<path>`, never `stash` or `checkout --`); **a file the block added has no base version, so it is removed for the red run** → runs the filtered tests → **parses** the output: an assertion failure ⇒ `RED`; a fatal, compile or import error ⇒ `RED_INVALID`, which proves nothing (a removed module that the test imports is the usual cause — such a test needs an assertion that fails against the base, not an import that crashes) → restores every journaled file byte for byte, **verifies each sha256**, deletes the journal (in a `finally`, so an ordinary error restores too) → when the red step was `RED`, runs again ⇒ `GREEN`. A characterization test (`proof: characterization`) is proven by assertion deletion. The ledger `proof` row records `mechanism` and `red_kind`; one `RED` + `GREEN` pair per proven test. SIGTERM mid-run leaves the journal; `forge proof restore <block> --run <r>` restores the exact hashes and refuses when no journal exists.

**How a test report is read (B86).** A `node:test` file is still classified from its console text. A runner that writes a JUnit XML report (PHPUnit, Pest, pytest, `swift test --xunit-output`) is classified from that report instead, because console text changes with the environment and is cut at 10 MiB. The reader fails closed: a report that is missing, empty, over 8 MiB, not UTF-8 or malformed, that has a `<!DOCTYPE` or `<!ENTITY` (no entity is ever expanded) or a character that is not an XML character, or that has an element other than `testsuites`, `testsuite`, `testcase`, `failure`, `error`, `skipped`, `system-out`, `system-err`, `properties`, `property` is unreadable. Each test's id is `classname.name` (or `name`). A `<failure>` is an assertion only when its `type` names one, or when it has no `type` and its `message` names one. The names: `AssertionError`, `ERR_ASSERTION`, `ExpectationFailedException`, `AssertionFailedError`, `Failed asserting that`, `XCTAssert…`, `XCTFail`, `Expectation failed` (Swift Testing), and pytest's `assert …`. Any other `<failure>` and every `<error>` is an error. One exception: `swift test --xunit-output` writes every failed XCTest as `<failure message="failed"></failure>`, with no type and no cause. Such a bare failure (no `type`, message exactly `failed`, an empty body; a body of only whitespace, as text or CDATA, counts as empty) counts as an assertion only when the console text has XCTest's assertion line for that same test (`<file>:<line>: error: -[Module.Suite test] : XCTAssert… failed` on macOS, `Suite.test : XCTAssert… failed` on Linux, or XCTFail's `: failed - <message>`) and shows no Swift crash (`Fatal error`, `Precondition failed`, `Assertion failed`, `Unexpectedly found nil`, `signal code`, `Illegal instruction`, `Segmentation fault`); a thrown error (`: failed: caught error`), a missing line or a crash leaves it an error. This table applies only to a runner that writes a report; a `node:test` file is still classified from its console text, as above. The RED step, first row that applies:

| when | verdict | `red_kind` |
|---|---|---|
| exit 0, no signal | `NOT_RED` | `none` |
| a timeout or a signal | `RED_INVALID` | `fatal` |
| the console text shows an import, compile or fatal error | `RED_INVALID` | `import` / `compile` / `fatal` |
| no report, or a report is unreadable | `RED_INVALID` | `error` (no readable test report) |
| no test ran (zero tests, or only skipped ones) | `RED_INVALID` | `error` (the filter ran no test) |
| any test errored, or failed without an assertion | `RED_INVALID` | `error` |
| at least one test failed on an assertion | `RED` | `assertion` |
| the run failed, but the report has no failure | `RED_INVALID` | `error` |

GREEN needs exit 0, a readable report, at least one test that ran, no failed or errored test, and every test that failed at RED present and passed; anything else is `NOT_GREEN`. The result keeps names only: `failed` is the count, and `failed_tests` lists at most 20 test ids of at most 200 characters each, never a failure message.

**Runners (B87).** A test file that is not a `node:test` file is proven through a `proof.runners` entry. Without one, `proof red-green` refuses it (exit 1): `only node:test files (.mjs, .cjs, .js) have a filtered test command in this version — add a proof.runners entry for it (see proof.md §2)`.

```yaml
proof:
  runners:
    - match: ["tests/**/*Test.php"]
      adapter: junit
      argv: [php, artisan, test, "{test_file}", --filter, "{test_filter}", --log-junit, "{report}"]
      env: {DB_CONNECTION: sqlite, DB_DATABASE: ":memory:"}
    - match: ["tests/**/test_*.py"]
      adapter: junit
      argv: [pytest, "{test_id}", --junitxml, "{report}"]
      timeout_s: 900
```

- **Keys.** `match`: a non-empty list of globs over repo-relative paths. `adapter`: `junit` (any runner that writes a JUnit XML report) or `swift`. In this version `swift` runs exactly as `junit`; its own filter and report reading come in a later version. `argv`: the command as an argv array, never a shell string. `env` (optional): variables added to the runner's environment, which never inherits a `GIT_*` variable. A value is never recorded: the signed row and the JSON output both hold only the names (`env_keys`). When the runner's own output echoes a value of 8 or more characters, code-forge masks it in every line it prints, as for gate env (below). `timeout_s` (optional): 60 to 7200 seconds per step, default 600.
- **Tokens.** An argv item that is exactly one of these is replaced: `{test_file}` the repo-relative test path; `{test_id}` `<file>::<case>`, or `<file>` with no case (a pytest node id); `{test_filter}` the case, regex-escaped; `{report}` the path where the runner must write its JUnit report. A token is a whole item, never part of one (`--log-junit={report}` is refused; give `--log-junit`, `"{report}"`), and never `argv[0]`. `validate` refuses: an empty `proof.runners: []` (leave the key out for no runner); an entry key it does not know (a typo such as `timeout`); an unknown adapter; a missing or empty `match`; a missing or empty `argv`, an `argv` given as one shell string, or an argv item that is not a string; a NUL character in an argv item or an env value; a token inside a longer item, a token as `argv[0]`, and a token-shaped item the adapter does not list (with an unknown adapter, one no adapter lists); an argv without `{report}`; an argv without a test token (`{test_file}`, `{test_id}` or `{test_filter}`: a proof must name its test); a `timeout_s` out of range.
- **Selection.** The runner list is read from the run's config snapshot, never from the live `.code-forge.yml`: `run start` freezes it, `run reload` refuses to change it, and while it is set no block may own `.code-forge.yml`. A coder cannot change the command that proves its own work. The first entry whose `match` covers the `--test` file runs it. No entry matches and the file is `.mjs`, `.cjs` or `.js`: the built-in `node:test` command, as before. A run started without a snapshot uses no runner.
- **Fail closed.** A runner whose argv has `{test_filter}` needs a case: `--test <file>` with no `::case` is a usage error (exit 2, no row): give `--test <file>::<case>`. An empty case (`<file>::`), and a test path or a case that starts with `-`, are refused (exit 2, no row). A snapshot list that is not a list, is empty, or has an entry that fails the checks above refuses the proof (`runner-invalid`, exit 1, no row): the entry is never run, never skipped, and the file never falls through to another entry or to `node:test`. A matched entry that has no runner hook is a usage error instead (exit 2, no row, no precheck).
- **The run.** Each step (RED, GREEN) gets a fresh report dir under the run's temp root, outside the work dir; the runner runs in the work dir (the export, or the tree under the lock) and the dir is deleted after its report is read. RED is classified from the report (the table above), GREEN by the GREEN rule above; a GREEN step that throws is `NOT_GREEN`, and the row is still written. A changed file that a runner's `match` covers is a test, never a source: it is not reverted. The journal, restore and signal rules are the same as for `node:test`.
- **The row.** The signed `proof` row and the JSON output add `runner: <adapter>`, `env_keys` (the entry's env variable names, `[]` without an `env`) and `failed_tests` (names only) when a runner was used. `failed_tests` is a bounded list of test names (at most 20, each cut at 200 characters, control characters removed), never a failure message. The full list of failed ids that GREEN checks (`failed_ids`) stays in memory and is never stored. A `node:test` row is unchanged.

## §3 The measurement export (R13) — `proof.isolation: export`, the default

Parallel blocks share one working tree, so nothing is measured there. `forge proof export <block> --run <r>` builds `.code-forge/export/<block>/`: (a) `git archive <base_sha>` extracted; (b) every path the base's `.gitattributes` marks `export-ignore` restored from `git show` — the hazard is real: repositories mark `/.github` and `CHANGELOG.md` that way; (c) every path in `proof.export.copy_untracked` that exists in the main tree added (`.env`, `.env.testing` by default; never anything under `.code-forge/`); (d) the block's owned files at their **current** content — new files included, and an owned file that existed at the base but is deleted in the tree is **removed from the export** too (listed under `removed` in the export's result), so a deletion is measured as a deletion; (e) the dependency dirs in `proof.export.link_dirs` symlinked read-only — except a **Composer vendor dir** (one holding `composer/autoload_real.php`), which is **copied** (listed under `copied` in the export's result): PHP resolves `__DIR__` through symlinks, so a linked `vendor` makes Composer's autoloader load `App\…` and `Tests\…` from the main tree, where another block's half-written file would leak into the measurement. Gates, red→green and the test-count delta run there; `--remove` deletes it at block close. A gate command that fails inside the export with a missing-file error is reported as `export.incomplete: <path>` with the sentence *add it to `proof.export.copy_untracked` or set `proof.isolation: lock`* — never as a red test.

**`proof.isolation: lock`** is the fallback for stacks whose tests cannot run from an export: `forge proof lock <block> --run <r>` takes a run-wide lock (Solo `lock_acquire` when present, else a lock file) that pauses other blocks' gate runs (`proof.busy`); the runner works in the shared tree with the journal; `forge proof unlock <block> --run <r>` releases it. The ledger flags `isolation: lock`.

**`proof.isolation: worktree` (B62a)** gives each block its own git worktree on its own branch. `forge block open` runs `git worktree add <dir>/<block> -b <branch> <base>` before anything is recorded. It stores `worktree {path, branch, base_sha}` on the block (the path is absolute), writes a signed `worktree.created {block, path, branch, base}` row before `dispatch`, and prints `worktree <path> · branch <branch>` between the open line and the pointer. The keys are under `proof.worktree`:
- `dir`: where the trees go, resolved from the repository top level (not from the workspace, even when the workspace is a subdirectory). The default is `../<repo-name>-worktrees`, where `<repo-name>` is replaced with the basename of the repository top level: outside the repository, so the main tree never shows the worktrees as untracked files. A `dir` through a symlink is recorded by its realpath.
- `branch`: a template, default `forge/{run}/{block}`. Only `{run}` and `{block}` are substituted, and the name must pass `git check-ref-format --branch`.
- `base`: the commit-ish the tree starts from. The default is the block's base (`--base`, else HEAD).

The open is refused (exit 1, `…; nothing was recorded`: no block, no row, no dispatch, no tree, no branch) for a block id that is not one plain path segment, an invalid branch name, a branch that already exists (checked again just before `git worktree add`, so a branch made after the plan is refused and kept, never deleted), something already at `<dir>/<block>`, a base that is not a commit, or a failing `git worktree add` (git's reason is named; a tree git registered anyway and a branch the failed add made are removed again, and anything that cannot be removed is named: `…; nothing was recorded, but left behind: <what> (<git's reason>) — remove it by hand`). If the open fails after the tree was made (a ledger row or the run record cannot be written), the tree is removed again (`git worktree remove --force`) with the branch the open made; the open's own error is shown, and anything that could not be removed is added to it: `Removing the worktree of the failed open left behind: the worktree <path> (<reason>); the branch <branch> (<reason>) — remove them by hand.`

A re-open of the same block (`--attempt`) reuses its worktree and branch as they are, printing `· reused` with no new `worktree.created` row. The block's base is then the tree's `base_sha`, not HEAD; a `--base` that names another commit is refused (exit 1, nothing recorded). `block rebase` is refused for a block with a worktree (exit 1): its base is the base of its tree. A tree still registered at the path but on another branch or a detached HEAD refuses the re-open (`worktree <path> is on <branch | a detached HEAD>, not <branch>`). A tree that is gone — removed by `--remove-worktree`, or its directory deleted by hand (git then lists it `prunable`; the open runs `git worktree prune`) — is added back at the same path on the same branch, with a new `worktree.created` row.

Overlap: two open blocks that each have their own worktree, at different paths, may own the same path (at `block open` and `block claim`). A block without a worktree is checked against every other open block exactly as under export, and `.code-forge.yml` is still never an owned file.

`forge block close <id> --run <r> --remove-worktree` (orchestrator only, forbidden to coders) runs `git worktree remove <path>` after a successful close. It never uses `--force` and always keeps the branch. A tree whose directory is gone refuses the close itself (see below); one that vanishes after that check (git lists it `prunable`) is pruned with `git worktree prune` and reported as removed (`worktree.removed`, exit 0).
- Success writes a signed `worktree.removed {block, path, branch}` row.
- A tree with modified or untracked files is kept. The command writes a signed `worktree.remove_failed {block, path, reason}` row and exits 1, and the block stays closed. It prints `block <id> closed`, then `block <id> worktree NOT removed: <git's reason> — the block stays closed; the tree stays at <path> (commit or clean it, then git worktree remove it)`.

Without the flag the tree stays. The flag on a block without a worktree is a usage error (exit 2).

`proof.isolation` and `proof.worktree` are fixed for the run: they are read from the run's config snapshot, and `run reload` refuses to change them. Nothing is ever pushed or merged, and no branch is deleted except one a failed open made itself.

**Where a worktree block's work is measured.** Gates, reviews and the close check of a block with a worktree run in its tree, never in the main checkout:
- `forge gates run --run <r> --block <id>` runs every gate with cwd = the workspace's place in the tree (leave `--cwd` out for a worktree block): the tree root when the workspace is the repository top, else the workspace's subdirectory inside the tree. `{test_files}` resolves the tests in the tree, and `gates.full_suite_threshold_files` counts the owned files in the tree. The gates themselves still come from the main tree's `.code-forge.yml`. The `gate.red` and `gate.done` rows and the JSON output carry `worktree: <path>`. The only `--cwd` accepted is that same place in the tree (compared by realpath), which is the same as no `--cwd`; any other `--cwd` is refused (exit 2): `gates run: block <id> of run <r> works in its worktree <path>, not in --cwd <dir> — drop --cwd (or give the worktree); no gate was run`. Any `--cwd=<dir>` (one argument with `=`, which is not read as `--cwd`) is refused too (exit 2), whatever it names: `gates run: block <id> of run <r> works in its worktree <path>, not in --cwd=<dir> — drop it (--cwd=<dir> is not read as --cwd); no gate was run`. For a block without a worktree, `--cwd` and `--cwd=<dir>` behave as before. A recorded tree that is gone, not a directory, lacks the workspace's subdirectory, or is not on the block's branch (another branch, a detached HEAD, or a plain directory), or is malformed (no absolute path, a branch that is empty or has control characters, a `base_sha` that is not 40 or 64 lowercase hex) refuses the run (exit 1): `gates run: block <id> of run <r>: <reason>; no gate was run`, e.g. `the worktree <path> is gone (removed or moved)`. `gates run` takes no count at `base_sha`: there is no test-count delta for a worktree block.
- `forge review-file`, from the main tree or from inside the tree, queues in the main tree's `.code-forge/queue`, where the worker runs. The file must lie inside the tree: a path with a `..` segment, an absolute path, or a symlink that leads out of the tree is refused (exit 1, nothing queued) with `{"status":"refused","reason":"bad-path","message":"…"}`. The content hash, the diff against the tree's `base_sha`, the peers' diffs and the fix hunks are read in the tree the run record names (never a path from the ticket). The ticket and the answer carry `tree: <path>` (the realpath), and the tree is part of the ticket id, so the same bytes in the main tree and in the tree are two tickets. A repeat request answers with the tree it was given, never with a path stored in the ticket. The worker reads the tree from the run record; a ticket whose `tree` is not that tree, or a ticket with no `tree` for a block that has one, is `review.unavailable` with `reason: worktree-mismatch` (paths compared by realpath). A block the run record gives no worktree is hashed in the main tree, wherever `review-file` is called (also from inside another block's tree), and its ticket carries no `tree`; only a run record that cannot be opened here (no such file, no permission) falls back to the tree `review-file` is called from. The packet's facts slot says `Worktree: the file is reviewed as it is in the block's worktree <path> (branch <branch>), against the block base.`. A file changed only in the main tree is never seen. A recorded tree that is gone, off its branch (`worktree-branch-mismatch`) or malformed, or a run record that exists but cannot be read (`run-record-unreadable`), refuses `review-file` (exit 1, nothing queued): `{"status":"refused","reason":"worktree-missing","message":"block <id>: the worktree <path> is gone (removed or moved); nothing was queued"}`. A tree that goes away after the ticket was queued makes it `review.unavailable` with `reason: worktree-missing` (`worktree-malformed` for a bad record, `worktree-branch-mismatch` off the branch), which is retryable.
- The `reason` for each refusal (gates run, block close, proof, `review-file`, and the worker's `review.unavailable`): `worktree-missing` the tree is gone; `worktree-not-dir` its path is a file; `worktree-malformed` the record has no absolute path, a path or branch with control characters, an empty branch, or a `base_sha` that is not 40 or 64 lowercase hex; `worktree-branch-mismatch` the tree is on another branch, detached, or a plain directory; `worktree-foreign` the path is a checkout of another repository (its git common dir differs from the workspace's), even on a branch of the same name; `worktree-workspace-missing` the tree lacks the workspace's subdirectory; `git-failed` git could not run (timed out, could not start, killed), with git's reason; `run-record-unreadable` the run record exists but cannot be parsed or names no workspace; `worktree-mismatch` (worker only) the ticket's `tree` is not the recorded one; `bad-path` (`review-file` only) the file leaves the tree.
- `forge block close` runs no gate (for any block), so no gate runs outside the tree at close: a worktree block's gates are `gates run --block <id>`, which runs in the tree. It measures the changed, unowned and reviewed files in the tree against its `base_sha`, committed on the branch and uncommitted alike. A change in the main tree or in another block's tree never counts. In the tree nothing is exempt: the main tree's dirty files at open (`tree_at_open`) excuse nothing, and a file a sibling open block owns is unowned too (`block <id> open: unowned_change <file>`, exit 1), since a sibling's work is in its own tree. When no owned file differs but owned files have review rows, the WARN says the work was likely `done outside the block's worktree (in the main checkout or another tree)`. A tree that is off its branch or malformed refuses the close too (exit 1, `block close: block <id>: <reason>, so its work cannot be measured; nothing was recorded`). A tree that is gone refuses the close (exit 1): `block <id>: its worktree <path> is gone (removed or moved), so its work cannot be measured — restore it on branch <branch> (git worktree prune, then git worktree add <path> <branch>) and close again; nothing was recorded`.
- `forge proof export <id>` and `forge proof red-green <id>` read the block's changed files, the `--test` file and the base in the tree (the workspace's place in it, against the tree's `base_sha`). The mutation proof runs in an export built FROM the tree, never in the tree itself: the export is written to the main tree's `.code-forge/export/<id>` (where `export --remove` and `proof restore` look), so the tree's files and `git status` are exactly as they were after the proof. This was chosen over measuring in the tree under the proof lock, because a crash mid-proof could leave a reverted source in the tree. The config (`proof.export.link_dirs`, `copy_untracked`) still comes from the main tree's `.code-forge.yml`; the link dirs and untracked files are taken from the tree. The `proof` rows are `isolation: export` and carry `worktree: <path>`, even if the main tree's `.code-forge.yml` was later edited to `isolation: lock` (no proof lock is asked for). A recorded tree that is gone, off its branch or malformed refuses (exit 1, no row): `proof <verb>: block <id> of run <r>: <reason>; no proof was run`. `proof lock <id>` on a worktree block is refused (exit 2, no lock, no row): `proof lock: block <id> is proven in an export built from its tree; proof lock does not apply`. A block without a worktree under `isolation: lock` still refuses `proof export` (exit 1, `proof export: proof.isolation is lock — use proof lock instead of an export`). `unlock`, `restore` and `export --remove` act only on the run's lock and the export directory, as before.

None of them pushes, merges or checks anything out: the work stays on the block's branch, and the main tree's HEAD and index never move. Blocks without a worktree (export, lock) are unchanged.

Test-count delta (blocks without a worktree) = the count on the block's filtered run in the export minus the same filter at `base_sha` (a second export, cached per base). The full suite runs only above `gates.full_suite_threshold_files`, also in the export. This delta belongs to the proof/export path; `gates run` never takes it.

**Related tests (B60).** A gate argv item that is exactly `{test_files}` (one whole item, never part of one, never the command, never the only item — `validate` refuses those — never a shell string) runs only the block's tests under `forge gates run --cwd <dir> --run <r> --block <id> [--slug <slug>]`: the paths given at `block open --tests` (the precise way), else the owned entries that are concrete files (no glob, no trailing `/`) and look like tests (a `test`/`tests`/`__tests__`/`spec` directory, or a name ending `.test.*`, `.spec.*`, `Test.php`, `_test.go`, or `test_*.py`). When the block owns more files than `gates.full_suite_threshold_files` (default 10; owned files: globs and directories count the tracked and new (not ignored) files they cover, a path not created yet counts as 1; outside a git repository each entry counts 1, and any other git failure runs the full suite with `reason: threshold`), the item is dropped with `reason: threshold`; when no test file is known, or `gates run` has no `--run/--block`, it is dropped with `reason: no_tests`. Dropped, the gate runs the full suite. The `gate.red` and `gate.done` rows say which: `scope: related` with `test_count`, or `scope: full` with `reason`; with `--run/--block` they also name `run` and `block`. A gate without the item runs exactly as before (no scope is worked out and its rows carry none). A test path that starts with `-` is refused, never passed as an option. Example: `test: [npx, vitest, run, "{test_files}"]`. For a worktree block (`proof.isolation: worktree`), leave `--cwd` out (`gates run --run <r> --block <id>`): the gate runs in the tree, `{test_files}` resolves the tests there, and the threshold counts the owned files in the tree, never the main tree's.

**Gate env (B60).** A gate may be `{argv: [...], env: {NAME: value}}`; the variables are added to that gate's environment (`env: {}` is no env). code-forge never prints or records an env value. Gate env is not a secret store. Child output is masked only for values of 8 or more characters. `gates detect`, results, ledger rows, `doctor` and `init` show only the names (`env_keys`); put secrets in the environment or a secret manager (`validate` refuses secret-looking values). A short value (`CI=1`, `MODE=test`) is not masked, so `npm test` stays readable. A block that edits `.code-forge.yml` shows the values in its own diff.

## §4 Verified and unverified stacks

The export is proven on the package's own example repository (a Node library with a `node:test` suite, `/.github` and `CHANGELOG.md` restored from `export-ignore`).

**PHP (Pest and PHPUnit, Laravel) under export: VERIFIED** on 2026-10-11 with PHP 8.4.25, Composer 2.10.2 and Laravel Framework 13.35.0 — a fresh `laravel/laravel` skeleton once on PHPUnit 12.5.38 (as shipped) and once on Pest 4.7.8 (`pestphp/pest` + `pestphp/pest-plugin-laravel` added). Re-run it with `CODE_FORGE_LIVE_PHP=1 node --import ./test/helpers/isolate.mjs --test test/proof/laravel-live.test.mjs` (needs `php`, `composer` and the network; skipped without the flag, so `npm test` never needs them; POSIX only — it was run on macOS, not on Windows). Each check builds the skeleton, commits it, adds the block's owned files (a new `app/` class, a unit test, a feature test that writes to the database), breaks a file the block does not own in the main tree (the main tree goes red), builds the export with the default lists and runs the detected gate `php artisan test --compact` there: exit 0, 4 tests passed. What a Laravel export needs:
- `vendor` in `proof.export.link_dirs` (the default): it is **copied**, not linked, as a Composer vendor dir (§3 (e)). Run `composer install` in the main tree first; the export never installs anything. The copy has a cost on every export: about 5 s and 69 MB for the Laravel skeleton where the file system cannot clone; code-forge asks for a copy-on-write clone (`COPYFILE_FICLONE`), which is near-free where it is supported (APFS, Btrfs, XFS). An absolute symlink inside `vendor` that points into the main tree (a Composer path repository: `vendor/acme/pkg -> <main>/packages/pkg`) is pointed at the same path in the export; relative links and links outside the main tree are kept.
- `.env` (and `.env.testing` when the project has one) in `proof.export.copy_untracked` (the default): Laravel needs its `APP_KEY`.
- A database the export can own: SQLite in memory. The skeleton's `phpunit.xml` already sets `DB_CONNECTION=sqlite` and `DB_DATABASE=:memory:`; when yours does not, set them as gate env: `test: {argv: [php, artisan, test, --compact], env: {DB_CONNECTION: sqlite, DB_DATABASE: ":memory:"}}`. A suite that needs a running database server is not isolated by the export — use `proof.isolation: lock`.

Detection: `composer.json` + `vendor/bin/pest` is `php-pest`; `composer.json` + `vendor/bin/phpunit` without Pest is `php-phpunit`. With an `artisan` file either runs `php artisan test --compact`; without one, `vendor/bin/pest` or `vendor/bin/phpunit` (a plain PHP project; detected, not run live).

A Vitest stack is **UNVERIFIED** until a real second consumer runs it; `proof.isolation: lock` is the documented fallback until then. `doctor` says which gate commands are on PATH.
